2 — OIDC Authorization Code Flow (Detailed Sequence)
🌐 Browser (User)
⚙️ Flask App
🏢 Azure AD (Entra ID)
# From To Description HTTP
Phase 1 — Login Initiation
1 Browser → Flask User visits any protected page (e.g. /dashboard). No session found. GET /dashboard
2 Flask → Browser @login_required saves requested URL in session. Redirects to /login. 302 /login
3 Flask — Flask MSAL generates a random state (UUID) for CSRF protection. Saved in session. Builds Azure AD authorization URL. state = uuid4()
4 Flask → Browser Redirects browser to Microsoft login page with all OAuth parameters. 302 /authorize?
client_id=...&
response_type=code&
scope=openid+profile+email&
state=UUID&
redirect_uri=/callback
Phase 2 — Microsoft Login
5 Browser → Azure AD Browser follows redirect to Microsoft login page. GET /oauth2/v2.0/authorize
6 Azure AD → Browser Azure AD returns login page. User enters org credentials (+ MFA if required by org policy). 200 Login HTML
7 Azure AD → Browser Azure AD validates credentials. Generates a short-lived authorization code. Redirects browser to app's callback URL. 302 /callback?
code=AUTH_CODE&
state=UUID
Phase 3 — Token Exchange (server-to-server)
8 Browser → Flask Browser follows redirect, delivers auth code to Flask. GET /callback?code=...&state=...
9 Flask — Flask CSRF check: state from request must match state saved in session. Mismatch → 400 error. state == session["auth_state"]
10 Flask → Azure AD Flask (via MSAL) makes a server-to-server POST to exchange the auth code for tokens. Includes client secret. Browser not involved. POST /oauth2/v2.0/token
grant_type=authorization_code
code=AUTH_CODE
client_secret=SECRET
redirect_uri=/callback
11 Azure AD → Flask Azure AD returns ID token (JWT) containing user claims. Client secret never leaves the server. 200 { id_token: JWT,
  claims: {
    name, email,
    roles: ["admin"],
    tid, oid, ... } }
Phase 4 — Session & Redirect
12 Flask — Flask ID token claims stored in server-side session (signed cookie). Token itself is discarded. session["user"] = claims
13 Flask → Browser Flask redirects user to the original page they requested before login. 302 /dashboard
14 Browser → Flask @role_required("admin") checks session["user"]["roles"]. Admin → page rendered. No role → 403. GET /dashboard
(with session cookie)
Key security property: The client secret and ID token are only ever exchanged between Flask and Azure AD (step 10–11). The browser only ever sees a short-lived authorization code, which is useless on its own. This is the primary security advantage of the Authorization Code Flow over the deprecated Implicit Flow.
3 — Application Flow Summary

🔵 SSO Login (all org users)

1
User visits any page (e.g. / or /about)
2
@login_required checks session — no user found, saves target URL
3
Flask → /login → MSAL builds Azure AD auth URL with CSRF state
4
Browser redirected to Microsoft login page
5
User signs in with org Microsoft account (+ MFA if required)
6
Azure AD returns auth code → browser → /callback
7
Flask validates CSRF state, exchanges code for ID token (server-to-server)
8
User claims stored in session → redirected to original page

🔴 Admin Role Check (RBAC)

1
Signed-in user visits /dashboard or /profile
2
@role_required("admin") reads roles claim from session
3a
✅ roles: ["admin"] present → page is rendered
3b
❌ No admin role → 403 Access Denied page shown
4
Admin tabs are also hidden in the nav bar for non-admin users (Jinja2 conditional)

🟢 Sign Out

1
User clicks Sign out
2
Flask calls session.clear() — removes local session data
3
Browser redirected to Microsoft logout endpoint
4
Microsoft clears the SSO session across all Microsoft apps
5
User returned to /login
4 — RBAC Design

RBAC Concept Mapping

RBAC ConceptImplementation
Rolesadmin (Azure AD App Role)
Role assignmentAzure Portal → Enterprise Apps → Users & Groups
Role claimroles: ["admin"] in ID token
Role check@role_required("admin") decorator
Access decisionFlask reads claim from session, allows or returns 403
UI enforcementAdmin tabs hidden via Jinja2 conditional

Assignment Required vs App Role

SettingControls
Assignment Required = No Who can sign in — all org users
App-Admin group → admin role Who gets roles claim in token
Non-admin user token roles: [] — signs in, sees Home/About
Admin user token roles: ["admin"] — sees all pages
These are independent settings. The group assignment does not restrict sign-in — it only grants an elevated role claim to specific users.

Extending Roles (future)

Adding more roles requires no code change beyond the decorator:
# Current
@role_required("admin")

# Future — either role
@role_required("admin", "editor")

# Future — team-specific
@role_required("finance-admin")
New roles are defined in Azure AD App Manifest and assigned to users/groups in the portal.

6 — Token Strategy
Token Requested Used Stored In Purpose
ID Token (JWT) ✅ Yes ✅ Yes Claims stored in session. Token discarded. User identity — name, email, roles, tenant ID
Access Token ❌ No ❌ No — Not needed — no Microsoft Graph API calls
Refresh Token ❌ No ❌ No — Not needed — re-login on session expiry

Scope Added By Purpose In ID Token
openid MSAL automatically Required for OIDC — enables ID token issuance ✅ Yes
profile MSAL automatically Adds name claim to ID token ✅ Yes
email Explicitly requested Adds email / preferred_username claim ✅ Yes
roles Azure AD automatically App role claims — emitted when App Roles are assigned. No scope needed. ✅ Yes (auto)
